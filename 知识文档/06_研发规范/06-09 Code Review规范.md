# 星云智联科技有限公司 Code Review 规范

| 版本 | 适用 |
| --- | --- |
| V1.0 | 研发中心 · 全体开发/测试 |

---

## 一、MR/PR 流程

```text
开发者完成功能 → 创建 Merge Request → CI 检查 → 至少 1~2 名 Reviewer 审查
   → 处理意见 → 合并到目标分支
```

- 使用 GitLab Merge Request，目标分支一般为 `develop` 或受保护分支。
- 关联对应 Issue/Task，写明改动说明与测试情况。

---

## 二、审查 Checklist

- [ ] 命名清晰、符合代码规范
- [ ] 无重复代码与无用代码
- [ ] 异常处理与日志合理
- [ ] 参数校验、权限校验（防越权）
- [ ] 敏感信息不落地（密码/日志脱敏）
- [ ] 事务、并发、缓存使用正确
- [ ] 单元测试 / 自测覆盖关键逻辑

---

## 三、提交规模建议

- 单次 MR 规模适中，便于 review。过大的改动应拆分提交。
- 每份 MR 应能独立编译、测试通过。

---

## 四、冲突与回退

- 提交前同步最新代码，减少冲突。
- 出现冲突在本地解决并自测后再推送。
- 如需回退，使用正确的 reset/revert，不随意强推受保护分支。

---

## 五、CI 关联

- MR 触发 CI（编译、静态检查、单元测试），未通过不得合并。
- 合并策略与保护规则以仓库配置为准。

---

## 六、评审时限与结论

- Reviewer 应在约定时间内（如 1~2 个工作日）完成审查。
- 结论可为通过 / 修改后通过 / 拒绝，并给出具体意见。

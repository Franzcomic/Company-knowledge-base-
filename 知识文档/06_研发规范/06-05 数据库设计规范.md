## 一、命名规范

| 对象 | 规范 | 示例 |
| --- | --- | --- |
| 库名 | 小写，下划线分隔 | `nebula_oa` |
| 表名 | 复数名词，小写下划线 | `sys_user`、`order_detail` |
| 字段 | 小写下划线 | `user_name`、`create_time` |
| 主键 | 一般用 `id`（自增/雪花） | `id BIGINT` |
| 索引 | `idx_` 前缀；唯一索引 `uk_` | `idx_user_id`、`uk_phone` |

### 冗余植言
- 表、字段命名语义清晰，避免系统保留字。

---

## 二、主键与约束

- 使用主键 `id`，合理选择自增或分布式 ID（雪花等）。
- 关键唯一约束加唯一索引（如手机号、邮箱）。
- 外键尽量在应用层维护，避免数据库级外键造成锁与性能问题。

---

## 三、字段类型选择

| 场景 | 推荐类型 |
| --- | --- |
| 整数 ID | BIGINT |
| 金额 | DECIMAL(20,2) |
| 短状态码 | TINYINT / INT |
| 长文本 | TEXT / LONGTEXT |
| 时间 | DATETIME / TIMESTAMP |
| 布尔/枚举 | TINYINT，避免魔法数字 |

- 金额禁止用浮点（float/double），避免精度问题。

---

## 四、索引设计原则

- 为高频查询条件的列建索引。
- 联合索引遵循「最左前缀」，字段顺序按选择性/查询频率排。
- 避免过多索引（影响写入性能）。
- 大表 DDL/加索引需评估锁表影响，必要时在线变更。

---

## 五、审计字段与软删除

- 通用表建议包含：`create_time`、`update_time`。
- 需要时增加 `create_by`、`update_by`。
- 软删除使用 `deleted`（0 未删/1 已删）字段，业务查询默认过滤；也可按需物理删除。

---

## 六、ER 设计

- 表结构设计前输出 ER 图，明确主外键与关联关系。
- 避免过度拆分与过度冗余，遵循第三范式为主、适度冗余为辅。

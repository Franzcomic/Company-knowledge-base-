# 星云智联科技有限公司 Git 使用规范

| 版本 | 适用 |
| --- | --- |
| V1.0 | 研发中心 · 使用 GitLab 的所有成员 |

---

## 一、Commit 规范

### 1.1 Commit 信息格式

```text
<type>(<scope>): <subject>

<body（可选）>
```

### 1.2 常用 type

| 类型 | 含义 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档更新 |
| `style` | 格式/样式，不影响逻辑 |
| `refactor` | 重构（非修复非新功能） |
| `test` | 测试相关 |
| `chore` | 构建/工具/依赖等杂项 |
| `perf` | 性能优化 |

### 1.3 示例

```text
feat(user): 新增用户注册接口

fix(order): 修复金额精度丢失问题
```

### 1.4 要求
- 一条提交只做一件事，subject 简短清晰（不超过 50 字符）。
- 提交信息用中文或英文统一风格，团队内部保持一致。

---

## 二、Branch 规范

| 分支 | 用途 |
| --- | --- |
| `master` / `main` | 生产稳定分支，受保护，仅可合并 |
| `develop` | 集成分支 |
| `feature/xxx` | 功能分支，从 develop 拉取 |
| `bugfix/xxx` | 缺陷修复分支 |
| `release/xxx` | 发布准备分支 |

### 命名示例
- `feature/login`
- `bugfix/payment-amount`
- `release/v1.2.0`

---

## 三、Merge 规范

- 功能开发完成后，从源分支发起 **Merge Request** 到 `develop`。
- 主流分支（master/develop）合并须通过 **Code Review** 与 CI 检查。
- 禁止未经 review 直接 push 到受保护分支。
- 冲突须在本地解决后再合并，避免破坏他人代码。

---

## 四、Tag 规范

- 发布时打 Tag，遵循**语义化版本**：`v主版本.次版本.修订版本`（如 `v1.2.0`）。
- 示例：
  ```bash
  git tag -a v1.2.0 -m "release version 1.2.0"
  git push origin v1.2.0
  ```

---

## 五、其他约定

- 拉取最新代码：先 `git pull` 再开发，减少冲突。
- 提交前使用 `.gitignore` 排除构建产物与敏感配置。
- 不要提交本地配置、密钥、密码文件。

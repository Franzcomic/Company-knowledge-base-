| 版本 | 适用 |

| V1.0 | 研发中心 |

## 一、URL 设计

### 1.1 基本原则
- 使用名词表示资源，**复数形式**：`/users`。
- 资源层级用 `/` 表示：`/users/{id}/orders`。
- 动作尽量通过 HTTP 方法表达，不在 URL 中使用动词（导出/搜索等例外可用 query 或专用端点）。

### 1.2 常见约定

| 方法 | 语义 | 示例 |
| --- | --- | --- |
| GET | 查询 | `GET /users/{id}` |
| POST | 新建/动作 | `POST /users` |
| PUT | 全量更新 | `PUT /users/{id}` |
| PATCH | 部分更新 | `PATCH /users/{id}` |
| DELETE | 删除 | `DELETE /users/{id}` |

---

## 二、HTTP 状态码

| 状态码 | 场景 |
| --- | --- |
| 200 | 成功 |
| 201 | 新建成功 |
| 204 | 删除/无内容成功 |
| 400 | 参数错误/校验失败 |
| 401 | 未认证 |
| 403 | 无权限 |
| 404 | 资源不存在 |
| 409 | 冲突（资源已存在） |
| 422 | 参数语义/业务校验失败 |
| 500 | 服务端错误 |

> 业务校验失败也可使用统一业务码（见《06-03 统一返回》）。

---

## 三、分页

### 3.1 请求参数
- `page`（页码，从 1 开始）
- `pageSize` / `size`（每页数量，设定上限如 100）

### 3.2 返回结构（统一分页对象）

```json
{
  "page": 1,
  "pageSize": 20,
  "total": 100,
  "list": [ ... ]
}
```

---

## 四、版本管理

- 通过 URL 前缀标识版本：`/v1/users`、`/v2/users`。
- 破坏性变更必须升版本，向后兼容接口保留旧版本。

---

## 五、错误返回体（统一）

```json
{
  "code": "1001",
  "message": "用户不存在",
  "data": null
}
```

- `code` 使用可读错误码，`message` 对用户友好，避免返回堆栈与敏感信息。

---

## 六、其他约定

- 幂等性：POST 创建考虑幂等键；PUT/DELETE 天然幂等。
- 接口文档：使用 Swagger/OpenAPI 维护，接口变更同步更新。
